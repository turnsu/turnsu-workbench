# 工作台、Skill OS 与 LOOP：公司脚手架整合及迭代方案

- 日期：2026-09-28
- 状态：已获准按阶段实施；完成度以架构现状及实际验收为准
- 桌面底层：产品负责人明确排除 Tauri 2；迁移 Electron + React + 私有 Node Host
- 专项调研：[桌面框架与 WorkBuddy 内存](2026-09-28-desktop-framework-memory-research.md)

## 1. 要交付的用户结果

优先让个人与约 8 人团队每天在工作台完成工作，并把有效方法沉淀为可复用技能。核心路径是：

```text
打开项目 → 使用自己的 Agent / 选择已有技能 → 给出目标与材料
  → 在原处回答问题或处理权限 → 查看真实文件与结果 → 关闭后继续
  → 把有效方法整理成 Skill → 在另一任务复用
  → 多步骤方法需要时保存为 Loop → 按需共享给团队
```

核心体验不以连接云端、配置全套自动化或理解流程引擎为前提。产品重点按“工作台与 Skill OS → 轻量 Loop → 后续复杂编排”推进。桌面平台选择穿插在前期验证中，不等到最终打包时才解决 Windows。

保留的职责来自[当前 Master PRD](../prd/2026-08-04-looloomi-team-intelligence-workspace-master-prd.md)及[桌面 / 云端边界](../architecture/desktop-cloud-boundary.md)：本机 Host 拥有原生会话和草稿；Product 拥有团队权限、共享对象和发布版本。底层实现可以改，但不凭 UI 状态授予权限、不上传私人原生历史、不以重连重放执行。

## 2. 已确认的现状和范围

| 对象 | 现状 | 本轮规划含义 |
| --- | --- | --- |
| 公司脚手架 | React 19、TypeScript、Tailwind v4、Base UI / shadcn；完整应用使用 TanStack Start、Nitro、Bun | 可选择性复用组件与主题；无需因复用 UI 将桌面改成 SSR 服务 |
| 桌面工作台 | 独立 React UI + Electron + Node Host；项目与会话在侧边，方法和团队管理集中在弹窗 | 优先改真实桌面入口及其主操作，不拿旧 Web 页面换皮替代 |
| Web 工作台 | React/Vite、Astryx 组件适配层，已有 Skill / Loop / 工作页面 | 保持已用能力可达；后续共享组件时评估迁移，Web 扩张不抢占桌面核心迭代 |
| Skill 使用 | 团队已发布方法能够经真实 Host 添加到项目；存在从成果整理、采用、试做和发布路径 | 需要把分散入口形成清楚的 Skill OS；不能假设统一的本机技能目录已经存在 |
| LOOP | 本机复用流程与团队云端运行路径并存，状态和授权不同 | 管理体验统一为简洁列表，执行位置必须清楚，不能混成一个无差别“运行” |
| 跨平台 | 当前打包及部分系统调用侧重 macOS | Windows 需要原生验收，框架自带支持不等于产品支持 |

脚手架已读到的固定版本：[`02203ea4ecdd2da3a2c22e7accc196f5b5e7ab35`](https://github.com/turnsu/frontend-scaffold/tree/02203ea4ecdd2da3a2c22e7accc196f5b5e7ab35)。仓库当前是可取用源码的应用脚手架，未见可直接依赖的公司 UI 发布包配置。其 LICENSE 为 MIT，包含原作者归属；复制组件时保留许可和来源，不把已有第三方来源抹去。

## 3. 信息结构与主要交互

### 工作台

- 左侧以当前项目和会话为主，保留“新任务”“打开项目”；一级产品入口仅“工作台”“Skill OS”。团队连接、设置位于次要区域。
- 中间只围绕当前工作：目标、对话、正在做什么、需要用户处理的事项、最终结果。工具明细默认折叠，失败原因与恢复动作保持可见。
- 文件 / 成果面板按需打开；默认不摆永久监控面板。任务切换保留草稿、选用 Agent、引用和未确认回执。
- 输入区将 Agent、模型、文件 / 方法引用组织在一起。Agent 与模型分别选择；本地 / 共享范围在提交附近明确显示。
- 不靠首页统计卡、流程状态大全或入口堆叠表达产品能力。

工作台完成证据是“能用自己的 Agent 在真实目录产生并打开结果、重开后继续”，不是聊天框已经渲染。

### Skill OS

这里优先解决“找到可用技能、理解作用、带入任务、改进和复用”，随后才是发布管理。

| 位置 | 首要内容 | 首要动作 |
| --- | --- | --- |
| 技能列表 | 名称、一句用途、来源 / 固定版本、可用性 | 在当前项目使用 |
| 技能详情 | 适用情境、需要的输入、可得到的结果、相关权限 / 依赖 | 选择自己的 Agent 并准备任务 |
| 本机 / 私有草稿 | 从哪次成果整理、哪里待检查、最近试做结果 | 继续调整或试做 |
| 团队发布 | 已确认版本、作者、适用说明、可见范围 | 采用固定版本；作者可准备新版 |

内容来源作为筛选或标签，不再变成几个难以区分的顶层“库”。本机全局、项目技能、团队固定版本仍保留真实归属；不能为了统一列表迁移用户原有 Agent 配置。

默认创建从真实成果进入“整理为技能”；导入已有技能保留为次要动作。查看 / 添加技能不自动调用模型，发送任务才执行。测试结果必须区分自动执行记录、人工确认和从未验证，不能用一个绿色徽章混在一起。

**当前能力缺口**：桌面已有团队方法列表和使用接口，但统一读取本机 / 项目技能、整理任务入口与草稿定位还需要明确数据来源。后续先做窄范围只读适配，复用原生文件与已有本地记录，不新增第二套 Skill 权限或发布数据库。

### 极简 LOOP

建议把 LOOP 放在 Skill OS 的“可复用流程”次级入口。工作台中仍可以引用和使用 Loop，不必先进入管理页。

管理首页只保留：**名称 / 用途、执行位置、状态、最近结果、一个主操作**。常见主操作为“使用”“继续草稿”或“查看结果”；停用、改名、版本等放到上下文菜单。

详情默认展示“这次要完成什么 → 需要什么材料 → 简短步骤 → 会得到什么”，再出现“本机试做”或明确的团队执行动作。表单按实际输入生成；云端依赖不足时指出缺什么，不展示编译器字段让用户自行翻译。

- 创建沿用“从成果整理”，顺序流程优先用可读步骤表达。
- 简单步骤的说明、输入和检查就地调整；复杂分支 / 条件的图形编辑通过“编辑依赖”进入。
- 保留已有画布能力：本次纠正明确要求管理极简，并没有要求删除所有依赖编辑能力。旧的 canvas-first 规则不再控制管理首页，复杂作者编辑仍可保留。
- 高级配置、原始 JSON、编译细节、运行诊断按需展开。
- 待审批、结果不确定、部分完成、失败不能被“简化”为完成；关键权限与共享范围仍在相关动作前明确出现。
- 第一轮不新增定时调度平台、复杂节点系统或新的执行引擎；既有能力通过需要时出现的入口保留。

示例：一个“周报整理”Loop 在列表上告诉用户用途、在本机还是团队执行、最近一次结果，以及“使用”。进入后提供本周材料，看到“汇总 → 整理 → 核对”的步骤和预计结果；只有修改依赖时才进入图编辑。

## 4. 公司脚手架的替换清单

源码依据为上述固定版本下的 [`src/components/ui`](https://github.com/turnsu/frontend-scaffold/tree/02203ea4ecdd2da3a2c22e7accc196f5b5e7ab35/src/components/ui) 和 [`src/styles/styles.css`](https://github.com/turnsu/frontend-scaffold/blob/02203ea4ecdd2da3a2c22e7accc196f5b5e7ab35/src/styles/styles.css)。

| 现有用途 | 可采用公司组件 | 采用方式与检查重点 |
| --- | --- | --- |
| 操作与状态 | Button、Badge、Tooltip、Spinner、Alert | 替换重复手写样式；核对禁用、加载、焦点、长中文及状态语义 |
| 输入与选择 | Input、Textarea、NativeSelect / Select、Field、Checkbox | 保留真实表单事件、中文输入法、校验与原生 Agent 权限选择 |
| 确认 / 详情 | Dialog、Sheet、Tabs、Collapsible | 重点检查焦点返回、Esc、嵌套层级和异步提交；现有原生 dialog 不因视觉统一而丢失能力 |
| 空态与导航 | Empty、Sidebar、Breadcrumb、DropdownMenu | 采用基础结构；导航内容由项目与会话决定，不复制后台菜单 |
| 对话 | Message、Bubble、MessageScroller、InputGroup | 先验证流式跟随、阅读历史不跳底、切换会话与分页，再替换当前滚动行为 |
| 技能 / Loop 列表 | Item / Table、Pagination、搜索输入 | 依数据密度用紧凑行；保留“已加载范围”与真实分页，不把本页搜索说成全库搜索 |
| 文件区 | 文件管理页面的行结构和工具条 | 只取交互结构，目录、权限和内容仍从实际项目读取 |
| 原生控制 / 复杂流程 | 无等价通用组件 | 保留业务实现；流程画布、原生批准、同步冲突处理不由样式组件替代 |

### 接入方式建议

1. 固定来源 commit，记录选用文件与必要依赖、许可。先在桌面客户端内维护一处选用组件；出现实际跨端共同消费者时再提取轻量共享层。
2. 公司主题 token 统一颜色、边框、间距与焦点；保留 Turnsu 现有品牌资产，检查深浅主题。Base UI 能提供部分键盘和焦点行为，但标签、对比度与实际组合仍需自己验证。[Base UI 官方说明](https://base-ui.com/react/overview/accessibility)
3. 保留项目现有业务调用和状态所有者。公司脚手架完整应用中的 TanStack Start、Nitro、演示数据、管理后台路由不作为桌面整合前置依赖。
4. 先替换一个完整黄金路径所需组件，再扩展到其余相关面板；不进行全仓标签批量替换。Web 的 Astryx 适配层在明确消费者后渐进迁移。
5. 包管理器、React 小版本及构建工具升级单独核查兼容性；组件复用不自动授权顺带全栈升级。

## 5. 桌面选型与内存工作的安排

具体事实、候选和测量方法见[专项调研](2026-09-28-desktop-framework-memory-research.md)。方案中的选择点是：

- 不再将 Tauri 作为候选；采用 Electron，保留 React 与 Node Host。决策依据是公司生态复用和扩展能力，内存预算仍须实测。
- 具体迁移、公司 llm-gateway 接入和验收按[迁移决策](2026-09-28-electron-gateway-migration.md)执行。
- 若现有 React 渲染本身无法满足关键原生体验，再考虑 Flutter 或分别采用 SwiftUI / WinUI。采用这些路线意味着公司组件主要复用规范与协议，不能声称 TSX 能直接复用。
- 决策先看真实黄金路径、macOS / Windows 可用性和长期内存曲线，再看迁移与维护成本。
- WorkBuddy 本机版本与官方历史修复已查明，但当前高内存根因仍未知。它是调查参照，不能成为不测量就放弃 Electron 或坚持 Tauri 的理由。

## 6. 分步迭代与退出条件

下表是实施顺序。人日为单一实现所有者、可用 Mac / Windows 测试机和正常服务条件下的粗估，不是交付承诺；每步结束按实际证据更新，不同时启动两条正式产品分支。

| 阶段 | 目标与工作包 | 交付及完成证据 | 依赖与粗估 |
| --- | --- | --- | --- |
| A：基线与选型验证 | 复核本次启动空白现象；捕获可工作的黄金路径；列组件映射；明确导航；完成 Electron 外壳替换、受限 IPC 与数据恢复验证 | 可对比的双平台资源曲线、原生交互结果、低保真信息结构、带理由的外壳决定。当前仅文档调研完成，实验未做 | 开发已授权；Windows 环境待落实；3–5 人日 |
| B：工作台与组件基础 | 落实选定外壳；打开项目、会话导航、对话 / 输入、文件 / 成果侧栏及公共控件；修复最高影响的渲染 / 刷新开销 | 真实目录 + 用户 Agent 完成文件任务；输入法、切换草稿、停止、权限回应和重开继续通过；macOS / Windows 都能操作 | A 的决策；5–8 人日，若外壳迁移另估 3–6 人日 |
| C：Skill OS 核心 | 来源清晰的技能列表 / 详情；现有方法添加与使用；从成果整理、试做、采用；团队发布 / 固定版本路径；补齐必要的本机只读目录适配 | 同一技能在另一真实任务复用；成功结果可打开；旧版本和本地修改不被覆盖；另一成员按授权使用固定版本 | B 的主路径；4–7 人日 |
| D：LOOP 极简化 | Skill OS 次级入口；紧凑列表、目标 / 材料 / 步骤 / 结果详情；高级编辑按需进入；保留本机与团队运行区别 | 一份真实方法从准备、试做、检查到再次使用可完成；失败、待审批和未知回执可恢复；旧流程仍可达 | B/C；2–4 人日 |
| E：双平台持续使用与试点 | 输入 / DPI / 窗口 / 授权返回 / 进程退出；长历史、多会话、预览、睡眠恢复；少量真实成员逐步使用 | 稳态内存、峰值、后台消耗与回落有记录；无数据丢失和重复执行；成员连续使用的实际结果。签名 / 公证单列交付证据 | 前述路径成立；3–5 人日，外部签名与账号等待不计入 |

资源检查从 B 就开始，每一阶段只回归受影响路径；E 负责持续运行与平台矩阵，不把性能问题留到最后。

外壳方向已确定为 Electron。A/E 的跨平台、持续使用与资源门槛仍保留；未取得 Windows 证据前，不标记双平台交付完成。

### 各阶段的可回退方式

- UI 迁移按页面 / 组件提交，保留旧入口可恢复；不改用户数据格式来配合视觉。
- 外壳实验使用隔离数据目录。确定迁移后才做正式数据目录、原生会话、密钥存储和旧版回退验证。
- 必要的数据迁移必须有可重开验证和兼容窗口；不能把删除旧文件当成完成整合。
- 相同任务的运行 / 共享请求复用原有回执，切换新版界面或外壳不重新执行。

## 7. 验收按用户结果组织

| 黄金路径 / 边界 | 必须看到的结果 |
| --- | --- |
| 本地开始工作 | 云端不可用时，项目、草稿、已有原生会话仍可进入；provider 联网需要单独提示 |
| 使用 Skill | 查看完整方法与来源 → 准备任务 → 用户发送 → 真实产物；查看或添加不产生模型调用 |
| 保存与复用方法 | 从结果整理的新方法可读、可试做，在另一个任务中产生可检查结果；发布有明确范围和版本 |
| 极简 Loop | 首次使用只接触必要输入与步骤；复杂依赖按需编辑；运行完成不冒充人工验收 |
| 切换与恢复 | 连续切换项目 / 会话，未保存输入和引用不丢；异常退出后核对原请求，不自动重放 |
| 团队边界 | 固定版本、读者范围、权限撤销和冲突仍由现有 Product 处理；不共享私密原生历史 |
| 跨系统 | 真实 Mac / Windows 操作，不用 Web 截图代替；中文输入、缩放、快捷键、原生文件选择及重开全部覆盖 |
| 长期资源 | 看应用组和 Agent 子进程的完整变化曲线；不靠少渲染一条结果、偷偷关闭工作或漏计子进程达标 |

现有本地 SQLite / 文件、Product HTTP / PostgreSQL 检查继续复用。纯控件替换只做相关行为和视觉验证；只有新增异步、权限或持久化行为才补对应回归，避免为改样式重建测试框架。

## 8. 当前可决策的结论与仍需补充的证据

可以确定的方向：公司组件和主题具备复用价值；桌面工作台与 Skill OS 是本轮核心；Loop 管理需要减少默认信息和操作；桌面底层迁移 Electron，Host 成本仍由实测定位。

仍需实测：Electron 的完整负载、WorkBuddy 在具体复现任务下的内存归因、Windows 设备与分发验证、已有 Skill / Loop 原生路径的完整视觉验收。

选型实验需落实团队最低系统 / 芯片 / 内存设备清单以及 Windows 测试机；未得到双平台证据前不宣布跨平台可交付。2026-09-28 首轮只完成本方案和专项调研；随后产品负责人授权先更新 Wiki 与开发约束，再按此顺序开发。当前实施结果以架构现状为准。
