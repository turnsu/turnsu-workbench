# 会话与内存

资源增长按数据加载和进程生命周期分别控制。更换桌面壳不能自动证明内存问题已解决。

| 对象 | 当前策略 |
| --- | --- |
| 启动快照 | 返回项目与 Agent 可用性；未选择项目时不返回会话 |
| 会话索引 | 按项目查询；每页最多 40 条；数据库内搜索完整历史；稳定游标翻页 |
| 当前消息 | 每页最多 40 条，通常限制在 256,000 字符；单条较长消息保持完整 |
| UI 历史 | 只保留最新页和当前查看的一页；分页替换，不无限累积 DOM |
| 原生 Agent | 打开历史不启动 Agent；执行或主动恢复时才建立连接 |
| 闲置连接 | 每 30 秒检查；最多保留 2 个闲置会话连接；闲置 5 分钟后释放 |
| 正在执行 | 运行、连接、等待权限和停止中的任务不参与闲置回收 |
| Codex | 释放闲置 thread 订阅；同一来源没有正在使用的任务后关闭 app-server |
| 正常恢复 | 复用原生会话 ID；Pi / Claude 不为健康会话重复导入完整可见历史 |

模型推理仍需要原生 Agent 读取当前任务自己的上下文，这部分由 Agent 管理。中断恢复可能需要协调原生日志：Claude 通过分页读取，Pi 的恢复接口仍可能返回该会话的完整消息；这与启动时加载所有会话是不同边界，必须分别测量。

回收不删除 SQLite 消息、项目文件或原生会话文件。重新选择历史只读取本地数据，再次发送任务才连接原生 Agent。

验收需分开记录 Host、Renderer、Electron 主进程与原生 Agent 的内存；使用相同历史规模、任务和等待时间观察启动、连续切换、运行及回收后的变化。合成 SQLite 负载只证明查询和传输边界，不代表真实模型或两种操作系统的长期内存结论。

To B 迭代还需要覆盖微信归档、解析进程、资料同步、插件、后台计划与记忆检索；这些不能通过界面分页自动获得资源边界。完整进程组的性能目标和 8 小时负载门槛统一维护在[迭代计划](roadmap.md)，尚未实测达标。当前共享文件的周期全量读取与哈希将改为增量观察和有界补扫；不把这一规划写成已完成优化。

多 Agent 扩展共用整台工作台的并发、闲置连接、历史缓存和解析预算，不按适配器数量成倍增加。发现安装 / 登录状态不能启动全部 Agent；只有选择执行或明确恢复时连接。所有由工作台启动的原生进程，无论采用客户已有安装还是企业提供环境，都计入完整内存与退出测量，并按 Agent / 版本分别记录；不能用 Pi 的结果替代 Claude Code、Codex 或新增适配器的结果。
