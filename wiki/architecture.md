# 系统架构

## 当前实现

以下为现有代码结构；完整多 Agent 适配、企业受管执行与客服业务闭环依照 [迭代计划](roadmap.md) 开发。已接入的局部能力与未验收范围分别注明。

```text
Electron 桌面 / React
  → 隔离 preload IPC
  → 私有 Node Host
      → 本地 SQLite（项目、会话索引、草稿、Agent 偏好、资料索引、可见消息）
      → 原生 Pi / Claude Code / Codex
      → 用户主动选择的微信桥交接与本机私有快照
      → 本机项目文件与 Skill
      → 可选 Product API（显式共享）

团队 Web → Product API → PostgreSQL / 执行控制 / Worker
```

桌面主进程管理窗口、文件选择器和系统加密凭据。渲染器没有 Node 权限；Host 不暴露公共 HTTP 端口。密钥不进入 SQLite、团队存储或 UI 日志。模型来源按会话固定，不能静默切换。

原生 Agent 拥有执行上下文、权限行为与原生会话文件。Host 保存原生会话 ID 和可见结果，以便连接回收后继续任务；它不复制用户全部 Agent 历史。原生模型执行可能按 Agent 自己的策略读取当前会话，其内存不能用 UI 分页上限推断。

团队服务只接收用户显式共享的工作、版本、文件和结果。服务端验证成员权限、版本、幂等和回执；网络中断或结果不确定不能触发自动重复执行。登录和团队同步不作为本地任务的前提。

新任务的 Agent 偏好当前保存在 Host 的本机 SQLite：本项目默认优先于个人默认，未设置时采用已发现的本机 Agent；用户仍可为一次新任务改选。已创建的会话固定原 Agent。企业允许名单、企业默认和第四种执行器尚未接入，不能把个人本机偏好称为企业策略。

微信桥消费者只在用户打开“微信资料”时列交接文件名，选择一份后读取 v1 manifest；导入时校验相对路径、原档大小和 SHA-256，将原档及 manifest 复制到 Host 私有目录，并把可查询的记录与文件索引写入 SQLite。列表与记录分页，预览正文限制为每条 600 字；明确引用到本机任务时，Host 从完整保存内容生成有上限的输入快照。团队事项拒绝直接引用私有微信导入；导入、模型推理与团队共享是独立动作。

## 拟实施的 To B 连接方式

在现有结构上补齐企业入口、材料导入和云端业务往返，不另建任务平台：

```text
员工 → 同一 Electron 工作台
  → 私有 Host：本地事项关联、材料索引、Agent 适配注册与能力检查
       → 客户选择的 Pi / Claude Code / Codex / 扩展执行器
       ← 微信桥适配器 / 用户选定文件
       → 明确授权的材料快照 + 业务任务合同
  → 现有 Product API：Work Item、权限、版本、批准、回执
       → 现有执行控制 / 公司的云端系统与 Agent
       → 业务连接器：CRM、订单、工单等权威系统
  ← 结果、依据、待补充信息和业务回执
  → 员工审核、继续跟进或确认交付
```

### 状态与授权所有者

- 本地工作可先拥有本地标识；共享时持久化映射到既有 Work Item。一次事项可有多个会话、执行和结果版本，但不出现两个独立业务状态源。
- Host 持有私有原生会话、草稿和被选材料；Product API 持有共享事项与权限；业务连接器引用客户系统的权威业务对象。模型输出不能直接改写这三类权威状态。
- 云端接收采用现有 outbox / 幂等体系，区分接收、执行、审核和业务交付；回调和轮询走同一游标 / 回执模型。取消、断网和未知结果不能触发盲目重做。
- 跨团队交接分享版本固定的资料、结论、限制、未决问题及结果，不复制隐藏推理、所有私人会话或供应商缓存。
- 企业策略控制受管工具、数据范围和预算，模型推理也属于数据外发。自带 Agent 的原生工具与批准保留，只有通过实际能力检查后才能承担要求受管策略的任务。

### 多 Agent 适配与执行绑定

现有 `packages/agent-host` 的 `pi.mjs`、`claude.mjs` 和 `codex.mjs` 已承担不同协议，`host.mjs` 仍按固定 Agent 类型分支；这提供了收敛基础，尚不是可注册的统一适配层。拟在同一 Host 内提取小型适配边界，由 `packages/contracts` 维护通用合同，复用现有状态和 native ID，不再新建一个常驻 daemon 或会话数据库。

| 适配责任 | 合同要求 |
| --- | --- |
| 发现与健康 | 安装位置、原生 / 适配器版本、平台、登录就绪状态及恢复入口；不把账号密钥返回 UI，不在发现时启动所有执行器或调用模型 |
| 能力描述 | 按具体版本和运行配置声明模型协议、原生命令 / 工作模式、流式事件、工具 / 批准、提问、历史列举 / 读取 / 恢复、附件、Skill 绑定、停止、用量等能力；支持、缺依赖和不支持分别表达 |
| 建立与运行 | 新建或恢复原生会话、提交输入、关联执行 ID；请求被接受与执行结束分开，不能仅凭 CLI 退出码或 RPC 应答报告业务完成 |
| 事件与交互 | 将文本、工具活动、批准 / 提问、产物、用量和终止状态映射到公共事件；保留必要的原生细节与来源。批准响应绑定当前原生请求，不能用企业批准跳过原生批准或反向扩大权限 |
| 停止与恢复 | 取消请求、确认结束、断线后核对状态、关闭闲置连接；结果未知要可见。SDK 不提供事件重放时明确恢复边界，不虚构游标或补齐未收到的结果 |
| 历史与上下文 | 只在用户选择后按支持能力读取 / 关联原生历史；同一 Agent 恢复原生 ID。不同 Agent 通过业务资料交接，不共享原生会话 ID 或隐藏上下文 |
| Skill / 工具绑定 | 可移植指令与执行器专属绑定分开；依赖与权限检查通过后再安装或运行，不假设所有 Agent 都采用相同 MCP 或配置格式 |

一次执行记录固定事项、执行者、适配器及版本、原生会话 ID、安装 / 账号配置引用、工作目录与模型来源；配置引用不包含密钥。选择顺序与首版名单由[迭代计划](roadmap.md#11-多-agent-执行与客户偏好首版必交付)维护。企业策略校验发生在运行前及敏感动作前；不能因为客户选择了某 Agent，就宣称该 Agent 具有未验证的策略执行能力。

客户偏好不是执行中的路由开关。跨 Agent 接续先确定原执行已停止写入、核对不确定的业务动作，再创建独立执行，传递被授权的目标、材料版本、成果、限制和未决问题。同一共享目录默认顺序执行；需要并行时明确不同工作副本或输出范围，并在合并时核验变更。交给其他成员的 Agent 还要验证执行环境的所有者授权、费用归属和结果接收权限。

`packages/agent-host/model-connections.mjs` 继续负责模型连接与凭据引用，协议兼容性由适配器能力提供给调用方；接入新的模型端点与接入新的执行 Agent 是两条独立路径。云端自定义 Agent 仍通过现有 Work Item 委派、状态和回执合同进入，不通过本地适配层绕过企业服务。

资源调度对所有适配器采用统一预算。未使用的 Agent 不常驻，账号 / 安装探测不读取全部历史；工作台启动的每个原生进程都纳入停止、退出与内存验收。

### 扩展边界

| 层 | 责任 |
| --- | --- |
| 公共客户端 | 工作空间、事项、材料、执行状态、审核、成果和恢复；不包含租户专属分支 |
| Agent 适配器 | 原生运行与会话协议、事件与批准映射、能力声明和健康状态；扩展注册不改变业务对象所有权 |
| 连接器 / 插件 | 文件来源、业务 API、受控工具；固定版本、权限声明、依赖和失败恢复；密钥不交给提示词 |
| Skill / Loop | 经过试跑的工作方法；引用已授权工具，不能覆盖服务端业务规则或授权 |
| 企业配置 | 可用方法、端点引用、字段映射、角色、保留期限、预算和品牌；经过 schema 校验，不作为任意脚本执行 |
| 云端业务系统 | 客户已有的复杂业务、长期执行和权威记录；通过任务合同对接 |

执行插件与原生 Skill 安装不是同一通道。现有原生 Skill 导出拒绝 runtime、tools、dependencies、可执行文件和隐藏配置的边界保留；新增能力通过单独审核的受控运行绑定提供，不把检查删掉。

微信桥继续拥有其 Swift 主体、原档和既有交付路径；工作台新增协议消费者和客服适配。当前计划采用两个仓库的兼容版本协作，不合仓、不搬入 Tauri 应答组件。导入契约、已有 v1 兼容和 Windows 边界由 [客服与微信桥](customer-service.md) 维护。

### 本地与云端的选择

决策同时考虑数据是否允许外发、所需工具在哪里、预算、网络和任务持续时间，不能简单按“复杂就上云”。需要本机文件 / 内网资源的步骤留在本地；需要关机后继续的步骤明确委派给已接收任务的云端执行者。资料只按选择的版本传递，禁止为恢复任务一次性读取所有上下文。

企业默认执行器由客户在已验证且符合策略的 Agent 中选择，按需准备依赖并保留已有原生环境；Pi 是正式支持对象之一，不是整个工作台固定的内核。现有 Electron 保持为桌面基础，内存策略围绕整个进程组、按需加载和执行生命周期验证；更换框架不是降低内存的验收证据。

## 源码职责

| 路径 | 职责 |
| --- | --- |
| `apps/desktop` | 桌面界面、Electron、打包 |
| `packages/agent-host` | 私有本地状态、原生 Agent 接入、资源回收 |
| `packages/agent-runtime` | 原生工具协议、Skill 安装、受限执行与 Worker |
| `packages/contracts` / `packages/product-client` | 共享协议与团队服务客户端 |
| `packages/agent-kernel*` / `packages/product-bridge` / `packages/agent-plugins` | 可选团队执行的内核与授权接线 |
| `apps/team-web` | 团队管理界面 |
| `services/product-api` | 权限、共享对象、Skill / Loop 版本、执行与持久化 |
| `deploy` | 可选服务部署资源 |

资源策略见 [会话与内存](memory.md)，开发入口见 [开发指南](development.md)。
